# Clarification on Task 2 forecast origin T

https://www.kaggle.com/competitions/2026-ieee-big-data-traffic-flow-bench/discussion/745700

**Alejandro Rendon B.** (2026-10-03T19:11):

Hi organizers,

Could you please clarify whether observations at the forecast-origin timestamp T itself are allowed as input for Task 2?

There appears to be a small inconsistency in the official materials:


The README describes each Task 2 window as providing “60 minutes of observations up to a forecast origin T”.

queue_ongoing is described as a condition where a queue is already visible at T.

The persistence baseline documentation says it reads the queue state at the forecast origin and repeats it through the six future steps.

However, the current official implementation appears to construct the history as [T−60, T) and treats reading T as leakage.


For competition eligibility, should participants interpret the allowed information set as:

A. timestamps ≤ T, including observations at T,

or

B. timestamps < T, excluding observations at T?

We want to make sure our implementation follows the intended Task 2 information contract.

Thank you.

---

**Traffice_Flow_Bench_Organizer** (2026-10-15T05:19):

A related question came in by e-mail, so we are answering it here for everyone. As with the onset property, conditioning a forecast on the documented window-selection procedure in config/synthetic_release_v1.json (the 360-minute spacing and the maximum persistence IoU) is within the rules. The Task 2 time rule still applies: for a window with origin T, only information stamped at or before T may be used, which includes only the origins in window_index.csv at or before T.

**Traffice_Flow_Bench_Organizer** (2026-10-15T04:06):

Thanks for laying this out. The answer is A: timestamps at or before T, including the observations at T. That is what the Rules say, and the Evaluation section now states it explicitly: the window history covers T-60 to T-5, and the row at T itself is released data and may be used.

You are right that the public repository was inconsistent. The comment in build_task2_persistence_submission.py that describes reading T as leakage is out of date, and BASELINES.md says the baseline reads the state at the origin when it actually uses the last history step, T-5. The baseline is simply more conservative than the rules require. We will fix both. Where the repository and the competition pages disagree, the Rules and the Evaluation section govern.
