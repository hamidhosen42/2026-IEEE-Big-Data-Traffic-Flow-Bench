# Task 2 future cells are present in the released mainline_states_masked files

https://www.kaggle.com/competitions/2026-ieee-big-data-traffic-flow-bench/discussion/740522

**Luigi ishii** (2026-09-09T21:48):

Hi organizers,

While working on Task 2 I noticed that the forecast horizon of every released queue window (T+5 … T+30) falls inside days that are published in corridors///mainline_states_masked/, for both the validation and the private split.

What I measured on the release (2 panels, all windows):


100% of the Task 2 target cells (window_id, timestamp, link_id) have a matching row in the published masked state files of the same split.

About 69% of those cells in validation and 63% in private carry a non-null observed speed_kmh. Applying the official rule speed <= v_cut to those observations reproduces the queue label directly; the remaining cells can be filled from neighbouring timestamps.


On the train split, where the truth can be checked, reading the labels this way gives an S_queue of about 0.9, against about 0.25 for the persistence baseline and about 0.5 for the best forecasting method I have. I did not submit anything built this way.

The README already handles the reverse direction (window cells are removed from the Task 1 targets because the windows publish raw observations), but the forward direction, from the state files into the Task 2 horizon, seems to remain open. Given the recent jump of the top of the leaderboard, it may be worth checking whether submissions rely on it.

A possible fix would be to blank the horizon cells of the released windows in the masked state files, or to re-score Task 2 only on cells that are not observable in the release.

Happy to share the measurement script privately if useful.

**Traffice_Flow_Bench_Organizer** (2026-09-09T22:38):

Thank you for this, and for reporting it rather than using it. That is exactly the right thing to do and we appreciate it.

We reproduced your finding. On the validation split, every Task 2 target cell has a matching row in the released mainline_states_masked files, and about 67 percent of them carry an observed speed. Applying the published queue threshold to those observations, with no forecasting and no neighbour filling, scores S_queue 0.641 against 0.252 for the persistence baseline. Your numbers are correct, and the effect is larger than we would have accepted had we caught it.

This is a flaw in how we built the release, not an ambiguity in the rules. The README closes the reverse direction, where window history would have given away Task 1 answers, but we did not close this one.

We are working out the fix now. There are two parts to it, and they are not the same question. Preventing further use is straightforward. Deciding what to do about submissions already made is not, and we would rather get that right than fast. We will post the decision here, with our reasoning, once we have it.

Thank you for the offer of the script. We reproduced the effect independently, so there is no need to send it. When we post the fix, we would welcome you checking it against your own measurement.

Until then, we would ask everyone to leave this route alone.
