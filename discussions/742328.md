# Task 2: in every queue_onset train window the queue first appears exactly at T+30

https://www.kaggle.com/competitions/2026-ieee-big-data-traffic-flow-bench/discussion/742328

**Dank Axon** (2026-09-21T14:06):

Hi everyone,
Reporting a regularity in how the Task 2 queue_onset windows appear to be selected. It does not expose any label and needs no data after T, but it makes onset windows much easier than intended, so I think everyone should know about it and you should decide whether it is acceptable.

What I see

For the train split, queue labels can be derived from train/mainline_states (speed <= 0.6 x free-flow speed). Doing that for the 40 shipped queue_onset train windows (8 corridors x 5):

In 39 of 40 windows the first queued cell in the horizon appears at the last step, T+30. In no window does a queue appear at T+5 … T+25. (The remaining window has no queued cell among the cells with an observed speed.)
The windows are small: median 3 queued cells, all at T+30.
This is what you would get if the selector scans origins forward in time and keeps the earliest origin whose 30-minute horizon contains a queue: that origin is, by construction, the one where the queue starts at the very end of the horizon.

Why it matters

If validation and private windows were selected the same way, then for a queue_onset window a participant knows, before looking at any traffic, that steps T+5 … T+25 are empty and that a queue starts at exactly T+30. The task collapses from "when and where will a queue form in the next 30 minutes" to "which few links are queued at T+30, given that one starts right then". On the shipped train onset windows, with their dates held out of training:

a general forecaster trained on windows where onset is spread over all six steps: IoU 0.57
the same features, trained only on windows where the first queue is at T+30 and predicting only that step: IoU 0.93
So roughly a third of an IoU point on half of the Task 2 windows comes from the selection rule rather than from forecasting skill. condition is published in window_index.csv, so the rule can be applied per window.

To reproduce

For each row of task2//train/window_index.csv with condition == queue_onset, take the six timestamps after forecast_origin from corridors//train/mainline_states, mark speed_kmh <= 0.6 * free_speed_kmh (from fd_parameters.csv), and record the first step with any marked link. It is step 6 every time.

Questions

Is this selection behaviour intended, and is a method that learns it from the released train windows within the rules?
If it is not intended, would you consider drawing onset origins at a random offset before the first queued step (so first appearance is spread over T+5 … T+30)?
For transparency: my current submission does use this, and I am happy to switch back to the general model depending on your answer. I would rather flag it now than have it surface at verification.

Thanks for the careful handling of the earlier reports.
